# Task and representation

Use this reference when several forms seem plausible, the request contains different reader tasks, or turning the material into a visual might add decoding work. The goal is a usable recommendation, not a catalog of diagram types.

## Identify the operation the reader must perform

Translate a broad aim such as “understand the program” into a question with an observable answer: find an eligible session, compare two schedules, explain why a step waits, or identify which part moves. Infer this from context where possible. A subject name alone does not select a representation.

Separate the task from the means proposed for it. “Use a timeline” names a form; “see which events can overlap” names the intended operation. Respect the requested form if it can carry that operation accurately. A change of form needs a reason tied to the question.

Identify what must be available together to answer it. This might be two estimates and their uncertainty, a rule and its exception, or a component and the boundary it belongs to. These are candidates for adjacent placement or a common view. They are not necessarily the most frequent words in the source.

Decide whether the reader needs an explanation, an index, or both. A guided explanation can reveal a mechanism in a deliberate sequence. An index benefits from stable ordering and repeated labels because the reader enters at an arbitrary point. A single artifact can support both, but its structure must make the two uses possible.

## Compare forms by the inference they permit

| Need | Useful candidates | What can make the candidate unsuitable |
| --- | --- | --- |
| Retrieve an exact item or value | Table, labeled list, indexed diagram | A decorative arrangement hides the lookup key or splits a row across views. |
| Compare corresponding attributes | Aligned table, dot plot, small multiples | Independent scales or changing item order make apparent differences unreliable. |
| Follow a conditional procedure | Decision table, branching flow, annotated sequence | Branches imply exclusivity or completeness the rules do not establish. |
| Understand changing state | Transition table, state diagram, selected histories | One observed history is presented as the full set of allowed transitions. |
| Find connections or shared membership | Relationship matrix, node-link view, overlapping groups | A tree silently assigns each item one parent despite multiple affiliations. |
| Understand physical arrangement or action | Annotated view, cutaway, sequence of views | An attractive viewpoint hides the connection or motion being explained. |
| Understand an unresolved account | Parallel explanations, evidence matrix, attributed annotations | A single causal chain manufactures agreement among conflicting sources. |

Do not treat these candidates as exclusive categories. A diagram can show a mechanism while a small table supplies exact settings. Recommend that combination only if each component answers a necessary question and their correspondence is explicit.

Use a sentence when the relation is already simple and the picture would merely restate it. Use a table when exact retrieval dominates and spatial relationships add little. A request for visual suggestions can legitimately receive that recommendation with a short rationale.

## Worked example: one source, different tasks

An invented community arts program offers **Printmaking** on Tuesday with an introduction session required, **Clay Studio** on Tuesday without a prerequisite, and **Choir** on Thursday without a prerequisite.

For “Which activity can I join on Tuesday without preparation?”, recommend a compact table with activity, day, and prerequisite. It keeps the two relevant attributes visible together. A timeline shows Tuesday versus Thursday, but does not by itself make eligibility easy to compare. Do not add registration times, capacities, or implied availability.

For “Why must I attend an introduction before Printmaking?”, the source only establishes a prerequisite. It does not explain the reason. A dependency sketch can show the requirement, but a causal illustration of safety training or equipment access would invent an explanation. State that the rationale is missing.

For “Show all activities by day”, grouping by day is sufficient. There is no need to force the eligibility comparison into the primary reading path. The same data legitimately supports different organizations.

## Define the handoff and its limits

Name the selected form, the actual entities or values it contains, the inference it supports, and the qualification that prevents its most plausible wrong reading. For an alternative, state the particular advantage and cost rather than calling one option “more engaging.”

If a constraint changes the recommendation, expose that dependency: a static handout may require simultaneous evidence that an exploratory interface could reveal interactively. Do not create a device matrix for an unspecified destination.

Counterexample to a universal “one message” rule: a comparison of competing interpretations may need two supported conclusions. The organizing question can be singular while its answer remains conditional or contested.

## Basis and limits

- [Brehmer and Munzner, A Multi-Level Typology of Abstract Visualization Tasks](https://www.cs.ubc.ca/labs/imager/tr/2013/MultiLevelTaskTypology/) distinguishes purposes, operations, and inputs/outputs. It is a task-analysis framework, not a universal form-selection algorithm.
- [Larkin and Simon, Why a Diagram is (Sometimes) Worth Ten Thousand Words](https://onlinelibrary.wiley.com/doi/10.1111/j.1551-6708.1987.tb00863.x) analyzes how representation changes search and inference in computational models. It does not establish that every diagram outperforms prose for human readers.

The selection procedure and invented example above are applications of these ideas, not experimentally validated skill instructions.
